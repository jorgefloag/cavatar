# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CAVATAR — a Next.js web app (Spanish-language, Mexico-focused) that turns a vehicle license plate into a digital mailbox. Anyone can look up a plate and read messages left for it, or send a message to a plate. Plate owners can "claim" their plate and, once approved, set a password to access their inbox. There's also a separate "verified profile" account system (email/password) that removes the anonymous rate limit on sending messages.

This codebase was originally scaffolded/edited via v0.app (see `generator: 'v0.app'` in `app/layout.tsx` and the `[v0]`-prefixed `console.log` calls scattered through client components — these are debug logs left from that workflow, not a required convention).

## Commands

```bash
pnpm dev      # start dev server (Next.js)
pnpm build    # production build
pnpm start    # run production build
pnpm lint     # eslint .
```

Package manager is pnpm (`pnpm-lock.yaml` present). There is no test suite configured in this repo.

Note: `next.config.mjs` sets `images.unoptimized: true`. `typescript.ignoreBuildErrors` is `false` (type errors fail `next build`), but running `tsc --noEmit` directly is still the faster feedback loop during development.

## Architecture

**Stack**: Next.js 16 (App Router) + React 19 + TypeScript, Tailwind CSS v4, shadcn/ui (New York style, Radix primitives under `components/ui/`), Neon (serverless Postgres) via Drizzle ORM, Clerk for the verified-profile auth system, Vercel Blob for banner image storage. All data access goes through Next.js Server Actions — there is no `app/api/`.

**Database**: `lib/db/schema.ts` defines the Drizzle schema (4 tables, see below); `lib/db/index.ts` exports the `db` client, built on `drizzle-orm/neon-http` + `@neondatabase/serverless` (HTTP driver — required for serverless/edge-style short-lived invocations, avoids exhausting Postgres connections). `drizzle.config.ts` at the repo root drives `drizzle-kit push` (schema is pushed directly, no migration files — deliberate while there's no production data; switch to `generate`+`migrate` once there are real users to protect). Both read `DATABASE_URL` from the environment.

**Data access pattern**: every route that needs the database defines a co-located `actions.ts` (e.g. `app/claim/actions.ts`, `app/inbox/actions.ts`, `app/send/actions.ts`, `app/verified/dashboard/actions.ts`, `app/verified/request/actions.ts`) with `"use server"` functions — one per mutation/query the page needs. Client components call these directly as async functions; nothing queries the database from the browser.

**Data model**:
- `claim_requests` — plate ownership claims: `plate_number` (unique), `email`, `vehicle_brand`, `car_name` (nullable, optional nickname the owner can set — surfaced to the admin table and, once the owner is authenticated, as the `/inbox` buzón title), `status` (`pending` | `approved` | `rejected`), `password_hash` (bcrypt, null until the owner completes setup), `failed_attempts` / `locked_until` (server-side brute-force lockout on the password-entry step — 5 attempts, 5-minute lock), `setup_token_hash` / `setup_token_expires_at` (SHA-256 hash of a one-time, 48-hour setup link — see below), `reviewed_at` (set by the admin panel on approve/reject/revoke). Resubmitting after a rejection upserts on `plate_number`, but only if the existing row isn't `approved` (`onConflictDoUpdate` with a `where` guard in `submitClaim`) — an approved claim can only be released via the admin panel's revoke action, never overwritten by a new public submission.
- `messages` — messages sent to a plate: `plate_number`, `alias`, `message`, `contact`, `created_at`. (Column names are English throughout — an earlier Supabase-era inconsistency between `message`/`mensaje` and `contact`/`contacto` was resolved during the Neon migration; there is no bilingual column pair anymore.)
- `verified_requests` — verified-profile applications: `user_email` (unique), `full_name`, `phone`, `use_case`, `status` (`pending` | `approved` | `rejected`), `reviewed_at`. Resubmitting (e.g. after a rejection) upserts on `user_email` rather than erroring.
- `banners` — one row per ad slot: `location` (unique, one of `landing` | `send` | `inbox`), `image_url` (Vercel Blob URL), `link_url` (nullable), `is_active`. See Banners below.

**Auth**: Clerk handles only the "verified profile" identity (`app/verified/*` — email/password login that lifts the anonymous send rate limit). It does **not** touch the plate+password inbox-access mechanism, which is a per-resource secret, not a user account, and stays fully custom (hashed server-side, verified in `app/inbox/actions.ts`, never sent to the client). `proxy.ts` (Next.js's renamed `middleware.ts` convention) runs `clerkMiddleware()` so `auth()`/`currentUser()` work anywhere in the app; `lib/auth/current-email.ts` wraps that into a single `getCurrentUserEmail()` helper used by every Server Action that needs to know who's logged in — the client never supplies its own email to a mutation. Login, register, and password reset (`app/verified/login`, `app/verified/register`, `app/verified/forgot-password`) are built on Clerk's newer "Signals" hook API (`useSignIn`/`useSignUp` from `@clerk/nextjs`, not the `/legacy` subpath) — methods are action-specific (`signIn.password()`, `signUp.password()`, `signIn.resetPasswordEmailCode.*`, `signUp.verifications.*`) and return `{error}` instead of throwing; session activation goes through `finalize({navigate})` instead of `setActive({session})`, via the shared `lib/auth/finalize-and-redirect.ts` helper used by all three pages. `lib/auth/clerk-error-message.ts`'s `getClerkErrorMessage()` reads `error.code` as a direct property on the returned `ClerkError` (falling back to `isClerkAPIResponseError` for anything that still throws as an exception). Client Trust (device verification when signing in from an unrecognized browser) is supported by the code — `login/page.tsx` has a dedicated `needs_client_trust` step built on `signIn.mfa.sendEmailCode()`/`verifyEmailCode()` — but whether it's actually enforced depends on the Clerk Dashboard's per-environment toggle (Development vs Production), which this file doesn't track. Registration has an extra email-verification-code step that the old fake-auth flow didn't have, because Clerk requires it by default. `lib/auth/revoke-other-sessions.ts`'s `revokeOtherSessions()` runs after a successful password reset (`forgot-password/page.tsx`, once `finalize()` has activated the new session) and closes every other active session for that user via the Backend API (`clerkClient.sessions.getSessionList()` + `revokeSession()`) — it takes no arguments and derives `userId`/`sessionId` from `auth()` rather than trusting anything the client passes in, since a Server Action is a public endpoint and a client-supplied session ID could otherwise be used to revoke a different user's sessions.

**Three independent flows, all under `app/`**:
1. **Inbox flow** (`app/inbox/page.tsx` — a thin Server Component that fetches the `inbox` banner slot, see Banners below — wrapping `app/inbox/inbox-content.tsx` for the actual client UI + `app/inbox/actions.ts`): plate lookup → claim status branching (`no_claim` / `pending` / `awaiting_setup` / `enter_password` / `inbox`) → message list. The client UI is wrapped in `Suspense` because it reads `useSearchParams` (supports deep-linking via `?plate=` from the hero form and `?focus=plate`). **Setting the password is never reachable by typing a plate number** — `awaiting_setup` only tells the visitor to check their email; the actual `passwordHash` can only be set via `app/inbox/setup/page.tsx` + `setupPasswordWithToken()`, which consumes a one-time token emailed when an admin approves the claim (`lib/claims/issue-setup-token.ts`, sent via `lib/email/send-setup-email.ts`/Resend). This closes a real vulnerability that existed before: plate numbers are public, so a direct "type the plate, set any password" path let anyone race the real owner for control of an approved plate's inbox. The token is single-use (the consuming `UPDATE` clears it atomically in the same statement it sets `password_hash`, guarded by `password_hash IS NULL` so a token can never overwrite an existing password) and expires after 48h; the admin panel's "Reenviar correo" button (`app/admin/claims/claims-table.tsx`, only shown when `status === "approved" && !hasPassword`) reissues it. **Trust assumption this doesn't change**: `submitClaim`'s `email` field is still freeform and unverified — approving a claim still relies on the admin having checked out-of-band that the email actually belongs to the plate's real owner. This fix stops the browser race after approval; it does not stop someone from submitting a claim with their own email before the real owner does.
2. **Claim flow** (`app/claim/page.tsx` + `app/claim/actions.ts`): plate + email + vehicle brand → inserted into `claim_requests` as `pending`, reviewed via the admin panel (`/admin/claims`, see below).
3. **Send flow** (`app/send/page.tsx`, a thin Server Component fetching the `send` banner slot, wrapping `app/send/send-form.tsx` for the client UI, + `app/send/actions.ts`): plate + optional alias/contact + message → inserted into `messages`. Anonymous senders are still rate-limited client-side to 3 messages/hour via `localStorage["cavatar_send_timestamps"]` (unchanged by the migration — still easily bypassed by clearing storage, still no server enforcement). Verified users bypass the limit; verification is checked server-side via `checkVerifiedStatus()`, which resolves identity through Clerk rather than trusting anything from the browser. Redirects to `/verified/login?returnTo=/send` and restores in-flight form data from `sessionStorage` after login (also unchanged).

The **verified-profile flow** (`app/verified/*`) is separate from the inbox/claim flow: `/verified` (landing) → `/verified/register` or `/verified/login` (Clerk-backed) → `/verified/request` (submit `verified_requests` application — a Server Component that gates on `auth()` and passes the Clerk-confirmed email down to a client form) → `/verified/dashboard` (Server Component that fetches application status server-side, renders a client view with a Clerk `signOut()` logout button).

**Banners** (`components/banner-slot.tsx` + `lib/banners/get-banner.ts` + `app/admin/banners/*`): one ad image slot per location (`landing` | `send` | `inbox` — `banners.location` is `unique()`, so there's no rotation/carousel; uploading a new image just replaces the old one). `BannerSlot` renders the image (clickable, `rel="sponsored"`, if `link_url` is set) or a dashed-border "Espacio publicitario" placeholder when there's no active banner for that location. Images live in Vercel Blob (`access: 'public'`); `app/admin/banners/actions.ts`'s `uploadBanner()` validates content type (JPEG/PNG/WebP) and size (2MB) before calling `put()`, and calls `del()` on the previous blob whenever a banner is replaced or removed so storage doesn't accumulate orphaned files. `next.config.mjs` bumps `experimental.serverActions.bodySizeLimit` to `3mb` — Next's 1MB default rejected uploads before the app-level 2MB check ever ran, and the real multipart body (boundaries + the `linkUrl` field) needs headroom above the raw file size. **`/`, `/send`, and `/inbox` are all marked `export const dynamic = "force-dynamic"`**: a plain `db.select()` doesn't hint dynamism to Next's static analysis the way `fetch()` does, so without this all three would have prerendered once at build time and frozen whatever banner existed then — defeating the entire point of managing banners without a redeploy. (`/claim` doesn't have this — its own env-var-driven content was already accepted as build-time-frozen, a separate, lower-stakes tradeoff made earlier.)

**Admin panel** (`app/admin/*`): the only UI for reviewing `claim_requests`/`verified_requests`/`banners` and moderating `messages`. Access is restricted to whatever emails are in the server-only `ADMIN_EMAILS` env var (comma-separated, checked case-insensitively by `lib/auth/is-admin.ts`'s `isAdminEmail()`) — a role in the database was deliberately avoided so access can't be granted by a mutable row, only by deployment config. Two independent layers enforce this, and only one of them is real security: `app/admin/(protected)/layout.tsx` (a Server Component gating every route inside the group) redirects unauthenticated visitors to `/admin/login` and non-admin sessions to `/`, but that's UX only — it never runs for a Server Action invoked directly. The actual boundary is `lib/auth/require-admin.ts`'s `requireAdminEmail()`, called as the first line of every admin Server Action (`app/admin/(protected)/{claims,verified,messages,banners,reports}/actions.ts`), returning `{ok:false}` instead of throwing so it fits this codebase's `{success, error?}` action convention. All pre-existing `/admin/*` routes live under an `app/admin/(protected)/` route group (parenthesized folder — no URL segment, just scoped layout inheritance) so that `app/admin/login`, a sibling of the group rather than a child, doesn't inherit that layout's auth guard; without the split, an unauthenticated visit to `/admin/login` would itself get redirected to `/admin/login` and loop forever. `/admin/login` (`page.tsx` + `admin-login-form.tsx`) is a deliberate duplicate of `/verified/login`'s Clerk Signals form (`signIn.password()`, `needs_client_trust`/Client Trust handling, `finalizeAndRedirect`) rather than a shared component — same mechanism, but without the "Crear cuenta" link or "perfil verificado" copy, redirecting to `/admin` (or `?returnTo=`) instead of `/verified/dashboard` on success. Duplication was chosen over extraction specifically to avoid any risk to `/verified/login`, which is already tested and in production. If a session is already active when `/admin/login` is visited, the page redirects immediately without rendering the form: an admin session goes to `/admin` (or `returnTo`), a non-admin session goes to `/`, mirroring how the `(protected)` layout treats a non-admin session on any other `/admin/*` route.

**Reports** (`app/admin/reports/*`): a 5-section analytics dashboard — growth (claim/verified approvals by week or month), activity (messages by day/week, active-vs-dormant approved plates at a 90-day no-message threshold), revenue (approved-plate count × ₡5,000, explicitly labeled an *estimate* in the UI since there's no renewal/expiration tracking at all — payment happens entirely outside the system), vehicle-brand demographics (`claim_requests.vehicle_brand` is freeform text, so the breakdown groups by `lower(trim(...))` to collapse casing/whitespace duplicates, not genuine typos), and claim review turnaround time. Each section is stat cards + a Recharts chart (`components/ui/chart.tsx`, previously vendored but unused until this) + a "Descargar CSV" button (`lib/csv/to-csv.ts` + `download-csv.ts` — hand-rolled CSV, no library, with a UTF-8 BOM so Excel doesn't mangle accented characters). The week/month and day/week time-series queries fill gaps with SQL `generate_series` so a period with zero activity renders as zero instead of a break in the trend line; the interval literals in that raw SQL are spliced in as text from fixed internal constants only, never parameterized — binding an integer parameter against `||` for string concatenation has no matching Postgres operator and throws. Approve/reject only apply to `pending` rows; revoke only applies to `approved` rows and, for a claim, also clears `password_hash`/`failed_attempts`/`locked_until` (cutting inbox access immediately) — for a verified profile, flipping `status` back to `rejected` is sufficient since `checkVerifiedStatus()` in `app/send/actions.ts` checks nothing else. There's no `revalidatePath` anywhere in this codebase (no precedent), so the admin tables use local optimistic state updates instead of re-fetching after a mutation. Message deletion is hard delete with a `console.error` log line beforehand (plate, admin email, message preview) as a minimal trail — there's no audit-log table and no way to recover a deleted message; see Roadmap.

**Styling**: `app/globals.css` is the active stylesheet (imported from `app/layout.tsx`, referenced by `components.json`'s `tailwind.css`). It defines a light, license-plate-inspired design system as CSS custom properties consumed by Tailwind v4's `@theme` — white background, carbón (`--foreground: #0B1220`) as the dominant color, and two disciplined accents: blue (`--primary: #1839A6`, reserved for the plate-frame element and focus states, not general emphasis) and red (`--destructive: #CE1126`, the hero's brand line plus real error/alert states). `:root` and `.dark` hold identical values — there's no dark-mode toggle anywhere in the app, `.dark` is just inert unused infrastructure. **`styles/globals.css` is dead code** — a leftover default shadcn/ui light theme that nothing imports; don't edit it expecting it to take effect, and prefer deleting it if doing cleanup.

**`.plate-frame` and `.brand-line`** (`app/globals.css`, plain CSS rules) are deliberately declared *outside* any `@layer` block. Tailwind v4's own utilities live in `@layer utilities`, which outranks `@layer components` regardless of where either is physically written in the file — a `.plate-frame` inside `@layer components` silently loses its 5px border to `Input`/`Card`'s own 1px `border` utility. Unlayered CSS beats every `@layer`-wrapped rule, so that's how these two are kept reliable. `.plate-frame` (thick blue border + two corner "screw" dots) is intentionally rare: the plate-search inputs on the landing hero and `/inbox`, and at most one "featured" card per message list (currently just "the most recent message," since `messages` has no read/unread tracking to genuinely target the newest-unread one).

Fonts, loaded via `next/font/google` in `app/layout.tsx`: Inter (`--font-inter`, body/forms/messages, the default `font-sans`), Archivo Black (`--font-plate`, **only** the "CAVATAR" wordmark and plate numbers shown as data/typed into a plate search field — never section titles), and Archivo 600/700 (`--font-label`, labels/nav/status text/timestamps, uppercase with wide tracking). Page-level H1s (e.g. "Iniciar sesión", "Reclamar placa") deliberately use neither special font — they're plain Inter bold, normal case.

Disabled buttons (`components/ui/button.tsx`) use a neutral `disabled:bg-muted disabled:text-muted-foreground disabled:border` treatment, not reduced opacity — on this palette, translucent carbón/blue reads as a washed-out pale blue rather than "unavailable," and solid-variant buttons have no border at all by default so a color-only disabled state was invisible on some screens (e.g. behind an unchecked consent checkbox).

`components/ui/` is the shadcn/ui component library (57 generated primitives) — treat as vendored code; prefer composing over hand-editing unless fixing a real bug. `components/*.tsx` (hero, explanation, features, faq, footer) are the marketing landing-page sections composed in `app/page.tsx`.

Path alias: `@/*` maps to the repo root (see `tsconfig.json` and `components.json` aliases: `@/components`, `@/lib`, `@/ui`, `@/hooks`).

## Roadmap / known gaps

- **No audit trail for message deletion.** The admin panel's `deleteMessage` is a hard delete with only a `console.error` log line (in Vercel's logs, not the database) as a trail — there's no way to recover a deleted message or formally audit who deleted what beyond that log line. Considered proportionate for a single-admin MVP; revisit if message volume or dispute risk grows.
- **`reviewed_at` has no matching `reviewed_by`.** `claim_requests`/`verified_requests` track when an admin last reviewed a row but not which admin, since `ADMIN_EMAILS` holds a single address today and the column would carry no information until there's a second admin. Add `reviewed_by` if that changes.
- **Resend needs a verified sending domain before real emails will deliver.** `RESEND_API_KEY` alone isn't enough — the `cavatarcr.com` sending domain (`no-reply@cavatarcr.com` in `lib/email/send-setup-email.ts`) needs SPF/DKIM/DMARC records added in the Resend dashboard, or claim-setup emails will land in spam or get silently dropped. Verify this before relying on the claim-approval flow in production.
- **Claim-email verification is still out-of-band.** The claim-setup-link fix (see Inbox flow above) closes the "race to set a password" vulnerability, but `submitClaim`'s email field is never independently verified (no Clerk-style confirmation) — the admin approving a claim is the only checkpoint that the submitted email belongs to the real plate owner. Someone submitting a claim with their own email before the real owner does is a different, unaddressed problem.
