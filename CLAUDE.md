# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CAVATAR — a Next.js web app (Spanish-language, Mexico-focused) that turns a vehicle license plate into a digital mailbox. Anyone can look up a plate and read messages left for it, or send a message to a plate. Plate owners can "claim" their plate and, once approved, set a password to access their inbox. There's also a separate "verified profile" account system (email/password) that removes the anonymous rate limit on sending messages.

This codebase was originally scaffolded/edited via v0.app (see `generator: 'v0.app'` in `app/layout.tsx` and the `[v0]`-prefixed `console.log` calls scattered through client components — these are debug logs left from that workflow, not a required convention).

## Commands

```bash
pnpm dev      # start dev server (Next.js)
pnpm build    # production build
pnpm start    # run production build
pnpm lint     # eslint .
```

Package manager is pnpm (`pnpm-lock.yaml` present). There is no test suite configured in this repo.

Note: `next.config.mjs` sets `images.unoptimized: true`. `typescript.ignoreBuildErrors` is `false` (type errors fail `next build`), but running `tsc --noEmit` directly is still the faster feedback loop during development.

## Architecture

**Stack**: Next.js 16 (App Router) + React 19 + TypeScript, Tailwind CSS v4, shadcn/ui (New York style, Radix primitives under `components/ui/`), Neon (serverless Postgres) via Drizzle ORM, Clerk for the verified-profile auth system, Vercel Blob for banner image storage. All data access goes through Next.js Server Actions — there is no `app/api/`.

**Database**: `lib/db/schema.ts` defines the Drizzle schema (7 tables, see below); `lib/db/index.ts` exports the `db` client, built on `drizzle-orm/neon-http` + `@neondatabase/serverless` (HTTP driver — required for serverless/edge-style short-lived invocations, avoids exhausting Postgres connections). `drizzle.config.ts` at the repo root drives `drizzle-kit push` (schema is pushed directly, no migration files — deliberate while there's no production data; switch to `generate`+`migrate` once there are real users to protect). Both read `DATABASE_URL` from the environment. The `neon-http` driver's one-request-per-statement model also means there's no `db.transaction()` available for interactive transactions — anywhere multiple writes need to succeed or fail together (see Broadcasts below), the code relies on a single atomic statement (e.g. `INSERT ... SELECT`) rather than a wrapping transaction.

**Data access pattern**: every route that needs the database defines a co-located `actions.ts` (e.g. `app/claim/actions.ts`, `app/inbox/actions.ts`, `app/send/actions.ts`, `app/verified/dashboard/actions.ts`, `app/verified/request/actions.ts`) with `"use server"` functions — one per mutation/query the page needs. Client components call these directly as async functions; nothing queries the database from the browser.

**Data model**:
- `claim_requests` — plate ownership claims: `plate_number` (unique), `email`, `vehicle_brand`, `car_name` (nullable, optional nickname the owner can set — surfaced to the admin table and, once the owner is authenticated, as the `/inbox` buzón title), `status` (`pending` | `approved` | `rejected`), `password_hash` (bcrypt, null until the owner completes setup), `failed_attempts` / `locked_until` (server-side brute-force lockout on the password-entry step — 5 attempts, 5-minute lock), `setup_token_hash` / `setup_token_expires_at` (SHA-256 hash of a one-time, 48-hour setup link — see below), `password_reset_token_hash` / `password_reset_token_expires_at` (a separate one-time, 1-hour token pair for self-service password recovery — see Inbox flow below for why this can't share the setup pair), `password_reset_window_started_at` / `password_reset_window_count` (shared rate-limit bookkeeping for reset requests and resent setup links, see below), `reviewed_at` (set by the admin panel on approve/reject/revoke), `notify_scheduled_at` / `last_notified_at` (nullable — new-message owner-notification bookkeeping, see Send flow below). Resubmitting after a rejection upserts on `plate_number`, but only if the existing row isn't `approved` (`onConflictDoUpdate` with a `where` guard in `submitClaim`) — an approved claim can only be released via the admin panel's revoke action, never overwritten by a new public submission.
- `messages` — messages sent to a plate: `plate_number`, `alias`, `message`, `contact`, `broadcast_id` (nullable FK to `broadcasts.id` — non-null marks the row as an official CAVATAR broadcast rather than a message from another user; see Broadcasts below), `owner_notified_at` (nullable — set once this message has been folded into a batched new-message notification email, see Send flow below), `created_at`. (Column names are English throughout — an earlier Supabase-era inconsistency between `message`/`mensaje` and `contact`/`contacto` was resolved during the Neon migration; there is no bilingual column pair anymore.)
- `verified_requests` — verified-profile applications: `user_email` (unique), `full_name`, `phone`, `use_case`, `status` (`pending` | `approved` | `rejected`), `reviewed_at`. Resubmitting (e.g. after a rejection) upserts on `user_email` rather than erroring.
- `banners` — one row per ad slot: `location` (unique, one of `landing` | `send` | `inbox`), `image_url` (Vercel Blob URL), `link_url` (nullable), `is_active`. See Banners below.
- `broadcasts` — one row per mass-message send: `admin_email`, `message`, `source` (`all` | `brand` | `list` — which of the three recipient modes was used), `brand_filter` (nullable, normalized `lower(trim(...))` brand string — only set when `source = 'brand'`), `recipient_count`, `recipient_plates` (nullable `text[]`, permanent snapshot — survives `undone_at` being set), `created_at`, `undone_at` (nullable). See Broadcasts below.
- `push_subscriptions` — one row per (plate, browser subscription) pair: `plate_number`, `endpoint` (unique together with `plate_number`, not alone — see Push notifications below), `p256dh`/`auth` (the subscription's encryption keys), `created_at`, `last_success_at` (nullable).

**Auth**: Clerk handles the "verified profile" identity (`app/verified/*`, lifts the anonymous send rate limit) and, since Etapa 2 of the sender-registration abuse plan, every `/send` sender's identity too (`app/send/login`, see Send flow below). It does **not** touch the plate+password inbox-access mechanism, which is a per-resource secret, not a user account, and stays fully custom (hashed server-side, verified in `app/inbox/actions.ts`, never sent to the client). `proxy.ts` (Next.js's renamed `middleware.ts` convention) runs `clerkMiddleware()` so `auth()`/`currentUser()` work anywhere in the app; `lib/auth/current-email.ts` wraps that into a single `getCurrentUserEmail()` helper used by every Server Action that needs to know who's logged in — the client never supplies its own email to a mutation. All Clerk-backed pages (`app/send/login`, `app/verified/login`, `app/verified/register`, `app/admin/login`) are built on Clerk's newer "Signals" hook API (`useSignIn`/`useSignUp` from `@clerk/nextjs`, not the `/legacy` subpath) — methods are action-specific and return `{error}` instead of throwing; session activation goes through `finalize({navigate})` instead of `setActive({session})`, via the shared `lib/auth/finalize-and-redirect.ts` helper used by every one of them. **Password is retired as the primary first factor everywhere except `/admin/login`** (see Admin panel below for why that one's different): `/verified/login` and `/verified/register` swapped directly to `signIn.create()`/`signUp.create()` + `signIn.emailCode.*`/`signUp.verifications.*`, same mechanism `/send/login` already used. `app/verified/forgot-password` is retired entirely (deleting a password you don't have is meaningless) along with `lib/auth/revoke-other-sessions.ts`'s only caller — that file is left in place, unused, rather than deleted, in case a future password-adjacent flow needs the same Backend-API session-revocation logic. `lib/auth/clerk-error-message.ts`'s `getClerkErrorMessage()` reads `error.code` as a direct property on the returned `ClerkError` for the string-coded Signals methods (falling back to `isClerkAPIResponseError` for anything that still throws as an exception) — but a *validation* error from `signIn.create()`/`signUp.create()` (e.g. "no account with this email") comes back as a `ClerkAPIResponseError` whose own `.code` is **always** the constant `"api_response_error"`; the real code only lives at `error.errors[0].code`. `isIdentifierNotFoundError()` in the same file exists specifically for that shape and must be used (not a bare `.code` check) anywhere code needs to detect "this email has no account" — found as a real, shipped bug during Etapa 3 testing of `/send/login`, where it silently broke the sign-in-vs-sign-up fallback. Client Trust (device verification when signing in from an unrecognized browser) is supported by the code — every login page has a dedicated `needs_client_trust` step built on `signIn.mfa.sendEmailCode()`/`verifyEmailCode()`, now triggered after whichever first factor just completed (email-code or, on `/admin/login`'s password fallback, password) rather than being tied to one specific method — but whether it's actually enforced depends on the Clerk Dashboard's per-environment toggle (Development vs Production), which this file doesn't track. Registration has an extra email-verification-code step that the old fake-auth flow didn't have, because Clerk requires it by default.

**Deployment order for the password→email-code migration (Etapa 3.5):** email-code as a first factor must be turned on in Clerk **Production** before this code ships there — Development and Production are separate Clerk environments with independently-configured factors, so testing locally against Development proves nothing about whether Production will accept an email-code sign-in attempt. Order: (1) enable email-code as a first factor in Clerk's Production dashboard; (2) push this code; (3) test `/admin/login`'s code path against **Production** specifically, not just Development; (4) only after that's confirmed working, turn off "Sign-up with password" in Production (this is also the moment `/admin/login`'s password-fallback view stops doing anything there). If admin login breaks in production at any point in this sequence, the fallback is a Vercel rollback (Deployments → previous deployment → Promote/Instant Rollback), not a hotfix under pressure. **`/admin/login`'s "Entrar con contraseña" fallback only ever works in Production, and only until step 4 above happens** — Clerk Development already has password disabled as a first factor (confirmed live via Clerk's own `/v1/environment` endpoint during Etapa 3), so in local/Development testing that button cannot be relied on as a safety net at all; it exists purely to protect the Production admin login during the window between this code shipping and step 4.

**Plate number normalization**: `lib/plates/normalize-plate.ts`'s `normalizePlateNumber()` is the single source of truth for what counts as "the same plate" — trim, uppercase, then strip everything that isn't a letter or digit. Costa Rican plates are physically written with a hyphen (`ABC-123`) but typed inconsistently everywhere they're entered (with/without the hyphen, spaces, mixed case); every plate-entry point in the app (`/claim`, `/send`, `/inbox`'s lookup/password verification and `?plate=` deep link, the admin plate search filters in `/admin/claims`/`/admin/messages`, and the uploaded-list parsing + pre-send re-check in `/admin/broadcast`) normalizes through this one function rather than reimplementing `.toUpperCase()` locally, so `"ABC-123"` and `"ABC123"` are always treated as the same plate. Client inputs strip the hyphen live as the user types, so what's on screen always matches what gets stored.

**Three independent flows, all under `app/`**:
1. **Inbox flow** (`app/inbox/page.tsx` — a thin Server Component that fetches the `inbox` banner slot, see Banners below — wrapping `app/inbox/inbox-content.tsx` for the actual client UI + `app/inbox/actions.ts`): plate lookup → claim status branching (`no_claim` / `pending` / `awaiting_setup` / `enter_password` / `inbox`) → message list. The client UI is wrapped in `Suspense` because it reads `useSearchParams` (supports deep-linking via `?plate=` from the hero form and `?focus=plate`). **Setting the password is never reachable by typing a plate number** — `awaiting_setup` only tells the visitor to check their email; the actual `passwordHash` can only be set via `app/inbox/setup/page.tsx` + `setupPasswordWithToken()`, which consumes a one-time token emailed when an admin approves the claim (`lib/claims/issue-setup-token.ts`, sent via `lib/email/send-setup-email.ts`/Resend). This closes a real vulnerability that existed before: plate numbers are public, so a direct "type the plate, set any password" path let anyone race the real owner for control of an approved plate's inbox. The token is single-use (the consuming `UPDATE` clears it atomically in the same statement it sets `password_hash`, guarded by `password_hash IS NULL` so a token can never overwrite an existing password) and expires after 48h; the admin panel's "Reenviar correo" button (`app/admin/(protected)/claims/claims-table.tsx`, only shown when `status === "approved" && !hasPassword`) reissues it. **Trust assumption this doesn't change**: `submitClaim`'s `email` field is still freeform and unverified — approving a claim still relies on the admin having checked out-of-band that the email actually belongs to the plate's real owner. This fix stops the browser race after approval; it does not stop someone from submitting a claim with their own email before the real owner does. Messages with `broadcast_id` set (see Broadcasts below) render differently in `inbox-content.tsx`: instead of the sender's `alias`, the card header shows a "CAVATAR · Oficial" label, since `alias`/`contact` are always `null` on broadcast rows.

   **Self-service password recovery** (`app/inbox/forgot-password/page.tsx` + `app/inbox/reset-password/page.tsx` + `app/inbox/password-reset-actions.ts`): closes the gap where someone who already set a buzón password had no way to recover it — the setup-token flow above only ever works once, before a password exists. Deliberately a **separate** token pair from the setup one — `claim_requests.password_reset_token_hash`/`password_reset_token_expires_at` — guarded the opposite way (`password_hash IS NOT NULL`, checked by `resetPasswordWithToken()`), so the two flows can never be confused: a setup token can never overwrite an existing password, and a reset token can never create one from scratch (a still-`awaiting_setup` claim just gets its original setup link resent instead — see below). Expires in **1 hour**, not 48h, and is single-use the same way (the consuming `UPDATE` clears the hash in the same statement that sets the new `password_hash`). `requestPasswordReset(plateNumber)` — the Server Action behind `/inbox/forgot-password` — always returns the exact same `{success: true}` response, regardless of whether the plate exists, is pending, `awaiting_setup`, or has a password: it does no database work itself before responding, scheduling all of it (the claim lookup, the rate-limit check, issuing whichever token applies, sending the email) inside `after()` (from `next/server`), so the response time can't leak which branch ran either. A shared per-plate cap — `password_reset_window_started_at`/`password_reset_window_count`, same start-anchored 24h pattern as the email/push notification caps, a fourth independent copy in `lib/claims/password-reset-window.ts` rather than shared code, same reasoning as the other two — limits **5 per 24h**, counting both a genuine reset and a resent setup-link equally, since both represent the same thing worth throttling: "we emailed this plate's owner a password-setting link today." Completing a reset also deletes the plate's `push_subscriptions` (same reasoning as `revokeClaim()` evicting them on revocation — cheap for the real owner to reactivate, correctly kicks out any device registered without their current knowledge) and sends a `lib/email/send-password-changed-email.ts` notice ("if this wasn't you, contact admin@cavatarcr.com"). `approveClaim()` and `revokeClaim()` (`app/admin/(protected)/claims/actions.ts`) both clear `password_reset_token_hash`/`password_reset_token_expires_at` too, so a stale link can never survive a status change out from under it. `/inbox/reset-password` carries the one-time token in its own query string, so `next.config.mjs`'s `headers()` sets `Referrer-Policy: no-referrer` scoped to that exact path only (confirmed with `curl` that `/sw.js`, `/manifest.webmanifest`, and `/inbox` itself are unaffected) — otherwise any outbound link clicked from that page would leak the token to that site's server logs via the `Referer` header.

   **`inbox-content.tsx`'s `handleReset()` race, found in production**: clearing `?plate=` via `router.replace()` alone wasn't enough to make "Volver" reliable — that navigation is asynchronous, so on a slow connection the auto-submit effect (watching `searchParams` + `pageState`) could still see the stale `?plate=` and re-run `lookupPlate()` before the URL update landed, silently snapping the screen right back to the one "Volver" was meant to leave (confirmed with a real headless-browser repro under Chrome DevTools' "Slow 4G" emulation — one extra request fired ~2.4s after a single tap). Fixed with `dismissedPlateRef`, a plain ref set synchronously inside `handleReset()` before any state update, checked by the effect on its very next run — refs carry no scheduling dependency the way a `router.replace()`-driven URL change does, so this closes the race outright rather than just making it less likely. `router.replace()` is still called too, now purely so the URL stays honest (reload, sharing the link) rather than as the anti-re-trigger mechanism itself.
2. **Claim flow** (`app/claim/page.tsx` + `app/claim/actions.ts`): plate + email + vehicle brand → inserted into `claim_requests` as `pending`, reviewed via the admin panel (`/admin/claims`, see below).
3. **Send flow** (`app/send/page.tsx`, a thin Server Component fetching the `send` banner slot, wrapping `app/send/send-form.tsx` for the client UI, + `app/send/actions.ts`): plate + optional alias/contact + message → inserted into `messages`. Sending is **mandatory-registration**, not anonymous: `send-form.tsx` gates every submission on `ensureSenderRegistered()`, redirecting a not-yet-registered visitor to `/send/login` (email-code or Google, via `getOrCreateSender()` — see Auth above) and auto-resubmitting the saved draft on return. `submitMessage()` then runs, in order: `checkSendPermission(sender, plateNumber)` (global `senders.isBlocked`, then per-plate `plate_sender_aliases.blocked` — both produce the identical silent fake-success response below, deliberately indistinguishable from each other; then the real rate limit, **3/hour standard, 20/hour verified**, a true sliding window via a plain indexed `COUNT` against `messages`, not the anchored-window pattern the email/push caps below use, since there's no shared third-party quota to protect here); then, for non-verified senders only, `checkContactRestriction()` (`lib/senders/validate-message-content.ts`) rejects a link, email, or Costa Rica-shaped phone number in "Mensaje"/"Nombre o alias" (links only — not phone/email — in "Contacto", since that field's own purpose is holding a phone/WhatsApp/correo) with a clear, field-naming error; then, on success, `getOrCreatePlateAlias()` assigns this sender's sequential `plate_sender_aliases.alias_code` ("Remitente 1", "Remitente 2"...) for this plate, first-contact only, with a bounded retry-on-conflict loop (no `neon-http` transactions) protected by real unique constraints on `(plateNumber, senderId)` and `(plateNumber, aliasCode)`. A **blocked** sender (global or per-plate) gets `{success: true, remainingThisHour: 0}` — byte-identical to a real send — with nothing written and no side effects; they are never told. Verified users bypass the hourly cap, the content restriction, and (not yet built) will eventually bypass the "Remitente N" display too — verification is checked server-side via `checkVerifiedStatus()`/`checkSendPermission()`'s own `verifiedRequests` lookup, never trusting the browser. After a successful insert, `submitMessage()` calls `scheduleOwnerNotificationIfNeeded()`, which — only for plates with an **approved** claim — schedules a batched "you have new messages" email to the owner via Upstash QStash (`lib/qstash/client.ts`), delayed 1 minute (`BATCH_DELAY_SECONDS`) so several messages arriving close together collapse into one email instead of one per message (tuned down from an initial 5 minutes once real usage showed messages can be urgent). QStash, like Vercel Cron, can only call a plain HTTP endpoint, so the delayed callback lands on `app/api/qstash/notify-owner/route.ts` — another deliberate `app/api` exception to the Server-Action convention, authenticated via QStash's own request-signing (`Receiver.verify()`, not a shared bearer secret). `claim_requests.notify_scheduled_at` prevents scheduling a second callback while one is already pending for that plate (a message arriving mid-window just gets picked up when the pending callback fires) — treated as stale and re-schedulable after 10 minutes (`STALE_SCHEDULE_MINUTES`, must stay comfortably above the webhook's own cooldown below) in case a callback never actually fires. The callback itself enforces two more rules before sending: a **5-minute cooldown** per plate (`claim_requests.last_notified_at`, `COOLDOWN_MINUTES`) so a sustained burst of messages can't notify the same owner more than roughly once every 5 minutes — if the cooldown hasn't elapsed, the callback reschedules itself for whenever it does rather than dropping the pending messages; and it only counts messages with `created_at` after the claim's `reviewed_at` and `broadcast_id IS NULL`, so neither a backlog that predates approval nor an official CAVATAR broadcast (already a deliberate one-to-many send) triggers a per-recipient email on top. **Muted senders** (`plate_sender_aliases.muted`, toggled from the buzón's "Remitentes" section) are excluded a third way: the callback's own query left-joins `plate_sender_aliases` and splits the result into `eligible` (counted and mentioned in the email) and `mutedSkip` (neither) — but both groups get `owner_notified_at` stamped together in the same run, specifically so un-muting later can never cause an old, already-skipped message to suddenly look "unnotified" and trigger a retroactive email. If `eligible` is empty (every pending message happens to be from a muted sender), `mutedSkip`'s rows are still stamped but no email goes out and the cooldown/window bookkeeping is untouched, same as the pre-existing "nothing pending" case. The email itself (`lib/email/send-new-message-notification-email.ts`) states only a count and a `/inbox?plate=` link — never the message content, since email can be intercepted. QStash needs `NEXT_PUBLIC_APP_URL` to be a real public HTTPS URL to call back to, so this flow can't be exercised end-to-end against `localhost`.

   **Per-plate daily notification cap** (`lib/qstash/notification-window.ts`, shared by both `app/send/actions.ts` and the webhook route so the two can never disagree about whether a plate is capped): protects two independent account-wide quotas — Resend's 100 emails/day and, more urgently, QStash's free-tier 1,000 publishes/day — from a single spammed plate. `claim_requests.notify_window_started_at` anchors a rolling 24h window for that plate (deliberately not derived from `last_notified_at`, which only records the most recent send and can't distinguish "2h into this window" from "23h into this window" once several sends have happened); `notify_window_count` counts notifications since that anchor. Once the count reaches `DAILY_NOTIFICATION_CAP` (12) within a still-live window, further messages keep inserting into `messages` normally but no further email goes out until the window expires (24h after its own start, not a calendar-day boundary) — a deliberate "simple" choice over building a guaranteed end-of-window summary callback: a pending message is just picked up whenever the next message naturally re-triggers scheduling after the window resets. The cap is checked in **two places**: first in `scheduleOwnerNotificationIfNeeded()` itself, which — critically — stops a capped plate from publishing to QStash at all (with the 1-minute batch delay, a plate spammed nonstop would otherwise keep generating a fresh QStash publish roughly every minute even while capped, since each capped send still clears `notify_scheduled_at` and lets the next message re-trigger scheduling — up to ~1,440 publishes/day for one plate, enough on its own to exhaust the account's entire QStash quota and silently break notifications for every other plate); and second, as defense-in-depth, in the webhook route right before sending, for any callback that was already in flight when the cap was reached. **Known tradeoff, accepted deliberately**: because the window anchors to its own start rather than a sliding lookback, a sender who sends one lone message (starting the window), waits ~23h, then bursts, can trigger ~11 more sends at the tail of that window and a fresh 12 the instant the next window opens — up to **~2x the cap** within roughly a 2-hour span. A third window can never join that cluster, since each window boundary is fixed exactly 24h after the previous window's own start. A legitimate sender who messages the same plate every ~23h forever never approaches the cap either way — the window keeps resetting every ~2 sends (~46h), confirmed by direct simulation against the real `claim_requests` columns. The 12th send in a window includes an extra line in the email telling the owner they've hit today's limit and to check `/inbox` directly.

   **Push notifications** (`lib/push/send-push-notification.ts`, `lib/push/push-window.ts`, `lib/push/web-push-client.ts`; activation UI in `components/push-notification-toggle.tsx` on `/inbox`, shown only once the buzón is unlocked): a near-instant channel that complements the email above rather than replacing it — `submitMessage()` fires `sendPushNotificationIfNeeded()` via `after()` (from `next/server`), called right after the (unchanged) email-scheduling line, so it runs once the response has already gone back to the sender, adding no perceptible delay, while Vercel still keeps the function alive until it finishes (unlike a bare un-awaited promise, which risks being torn down mid-flight). Unlike email, push isn't batched — it fires once per message, with no callback to filter inside later — so a **muted** sender (`plate_sender_aliases.muted`) is checked right there in `submitMessage()`, using the alias row `getOrCreatePlateAlias()` already just returned, and the `after()` call is skipped entirely rather than letting `sendPushNotificationIfNeeded()` itself try to figure out which message/sender triggered it.

   **Rate limiting** lives in three new `claim_requests` columns — `push_last_sent_at`, `push_window_started_at`, `push_window_count` — and is deliberately independent of the email channel's: `lib/push/push-window.ts` duplicates the small anchored-24h-window pattern from `lib/qstash/notification-window.ts` rather than importing it, so the two channels' limits can never drift into each other by accident. A **60-second minimum gap** per plate (`push_last_sent_at`) skips sending a push for a message that arrives too soon after the last one — safe to skip, since `tag`+`renotify` (see below) would collapse a same-plate burst visually anyway, and the message is still saved and still covered by email/`/inbox`. A **cap of 20 per rolling 24h window** (`push_window_started_at`/`push_window_count`, the same start-anchored design and ~2x-the-cap boundary-burst tradeoff as email's 12/day) is higher than email's cap since push has no shared third-party account quota to protect the way Resend/QStash do. `web-push`'s `sendNotification()` is called with **`urgency: "high"`** and **`TTL: 14400`** (4h): `urgency: "high"` is the Web Push standard's (RFC 8030) signal that Android shouldn't defer delivery to the next Doze maintenance window — confirmed this maps to FCM's own high-priority delivery, which attempts to wake the device immediately even in Doze (still subject to Android's per-app standby-bucket quota, so not an absolute guarantee); the 4-hour TTL lets a push survive a brief loss of signal or a sleeping device without being silently dropped by the push service, while not resurrecting a notice old enough to have lost its relevance (the previous, pre-tuning value was 60 seconds, far too short for this). A subscription whose endpoint responds 404 or 410 is deleted — every row sharing that endpoint, since one device can be bound to several plates — and any other send failure is only `console.error`'d, never silent.

   **`push_subscriptions`** (`plate_number`, `endpoint`, `p256dh`/`auth` — the subscription's own encryption keys, `created_at`, `last_success_at` nullable) is keyed `UNIQUE(plate_number, endpoint)`, not on `endpoint` alone: a browser has exactly one push subscription per origin, but nothing stops that same device being bound to several plates the owner controls. Activating push re-verifies the buzón password through the same `failed_attempts`/`locked_until` lockout as unlocking the inbox (`lib/claims/verify-claim-password.ts`, extracted so `app/inbox/actions.ts` and `app/inbox/push-actions.ts` share one implementation). Capped at **5 devices per plate**, oldest evicted silently (no error shown) once a 6th activates. `public/sw.js` only handles `push` and `notificationclick` — no `fetch` handler, no caching — and is registered lazily on activation, not on page load, so Phase 1's installable-only PWA stays inert for anyone who never opts in; the `tag` is scoped per plate (`cavatar-{PLACA}`) with `renotify: true`, so a new message replaces the visible notification for that plate instead of stacking, without silently swallowing a still-unread notification for a different plate on the same device. `revokeClaim()` also deletes that plate's `push_subscriptions` rows, same as it already clears the inbox password.

   **VAPID identity**: three env vars sign every outgoing push — `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (Vercel type **Config**; it's embedded in the client bundle at build time regardless, same `NEXT_PUBLIC_` baked-at-build-time caveat as the SINPE/WhatsApp vars on `/claim`), `VAPID_PRIVATE_KEY` (Vercel type **Secret**, server-only), and `VAPID_SUBJECT` (Config, a `mailto:` contact address the Web Push protocol requires). Generated once locally via `npx web-push generate-vapid-keys` and written directly into `.env.local`. Rotating these keys invalidates every existing subscription without warning — the browser's encryption is tied to the exact public key it was given at subscribe time — so treat them as close to permanent.

   **iOS is the weak link**: Safari only supports Web Push from a PWA already installed to the home screen (iOS/iPadOS 16.4+) — opened inside a plain Safari tab, there's no way to even offer activation. `PushNotificationToggle` detects this (iOS user agent, and not `display-mode: standalone`/`navigator.standalone`) and shows an instruction to install first, reusing Phase 1's existing install flow, instead of the usual "Activar avisos" button.

**Remitentes** (`app/inbox/senders-actions.ts` + `app/inbox/plate-senders-section.tsx`, a collapsible section in the buzón, lazy-fetched only when opened): lists every distinct sender who's written to this plate — `aliasCode`, a message count, and the Silenciar/Bloquear toggles — using `plate_sender_aliases.id` as the one opaque identifier the client ever sees for a sender, never `senderId`/`clerkUserId`/`email`. Both `muteSender()`/`blockSender()` require a valid inbox session for this exact plate (same `verifyAndRenewInboxSession()` as the moderation actions above) and independently confirm the `aliasId` they're given actually belongs to that plate before touching anything — a tampered `aliasId` copied from a different plate's session fails closed, not silently. **Message-count convention**: counts only `deletedAt IS NULL` messages — an archived message still counts (archiving is an owner-only declutter action, never a signal about the sender; see Message moderation below), only a soft-deleted one is excluded, consistent with every other "how many messages" surface in this codebase. Each message's displayed sender identity (`app/inbox/actions.ts`'s `buildSenderLabel()`) is always the system-assigned `"Remitente N"` first, never the sender's own free-text "Nombre o alias" at face value — that text, if present, is appended explicitly as a self-reported claim (`Remitente 3, dice llamarse "Juan"`), so it can never be mistaken for a verified identity. A message with no matching alias row — either `senderId IS NULL` (sent before Etapa 2) or, rarer, `getOrCreatePlateAlias()` exhausted its retries (see Send flow above) — falls back to `"Remitente anterior"`, the same label either way, since from the owner's side there's no meaningful difference between the two causes.

**Admin-side sender moderation** (Etapa 6 — `lib/senders/block-sender-globally.ts`, `lib/senders/anonymize-sender.ts`, `lib/senders/resolve-sender-display.ts`, `lib/admin/fetch-messages-with-sender.ts`, `lib/admin/fetch-reported-messages.ts`, wrapped by thin, gated calls in `app/admin/(protected)/messages/actions.ts`): the admin's `/admin/messages` table, its CSV export, and the "Reportados" tab all show the sender's real **email** — unlike the buzón owner, who only ever sees `"Remitente N"` (Etapa 5's Remitentes section above is unaffected by any of this). This is the same asymmetry the admin panel already has everywhere else (it already sees `claim_requests.email`/`verified_requests.user_email` directly). **Global block** (`blockSenderGlobally()`) sets `senders.isBlocked`/`blockedAt`/`blockedBy` — independent of, and in addition to, a plate owner's own per-plate block from Etapa 5 — and takes effect on every plate immediately, since `checkSendPermission()` already checks `isBlocked` first; validates the `senderId` exists first, returning a clear error otherwise rather than silently no-op'ing. None of these `lib/` functions call `requireAdminEmail()` themselves — that gate lives only in the Server Action wrapping each one — specifically so the real query/mutation logic stays directly testable without a live Clerk admin session (the admin login itself still can't be automated, same Cloudflare limitation as everywhere else Clerk is involved in this codebase).

**Right-to-erasure (Ley 8968)**: `anonymizeSender(senderId)` is the manual procedure for when someone asks to have their sender data erased — deliberately **not** wired to any admin UI button, since this is rare enough that an accidental click is a worse risk than one extra manual step. Run it (e.g. via a one-off script, same pattern used throughout this codebase's own testing) only once the person's underlying Clerk account has already been deleted out-of-band — if the Clerk account still exists and they log in again, `getOrCreateSender()` would resync `senders.email` from Clerk's still-real address and silently undo the anonymization. It rewrites `senders.email` to `"eliminado-<id>"`, clears `reported_sender_email_snapshot` on every `message_reports` row naming that sender, and clears `messages.contact`/`messages.alias` (set to `null`) on every message that sender ever sent, on any plate — those are free-text fields the sender filled in themselves and could hold a phone number, a different email, or their own name. The snapshot clearing matters independently of what any UI derives, since that raw text is itself stored PII and must not persist once erasure happens, even though a live join to the (now-rewritten) sender row would already resolve to the same anonymized label either way. Deliberately **not** cleared: the message body itself (`messages.message`) and a report's `messagePreview` — that's the content of an exchange with another person (the plate owner), not solely the sender's own account data; see Roadmap for the open legal question on whether erasure needs to reach that far too. `resolveSenderDisplayEmail()` is what turns the literal `"eliminado-<id>"` string into `"Remitente anonimizado"` everywhere an admin screen would otherwise show it verbatim.

The **verified-profile flow** (`app/verified/*`) is separate from the inbox/claim flow: `/verified` (landing) → `/verified/register` or `/verified/login` (Clerk-backed) → `/verified/request` (submit `verified_requests` application — a Server Component that gates on `auth()` and passes the Clerk-confirmed email down to a client form) → `/verified/dashboard` (Server Component that fetches application status server-side, renders a client view with a Clerk `signOut()` logout button). The request form's **"Nombre comercial"** field (separate from "Nombre completo", which stays an admin-facing identity check, not anything shown publicly) is the applicant's own public display name — its help text says so directly: "Este nombre lo verán los dueños de placas cuando les escribas. El equipo lo revisa antes de aprobar." `submitVerifiedRequest()` (`app/verified/request/actions.ts`) resolves `clerkUserId`/email server-side and delegates the actual write to `lib/senders/apply-verified-request.ts` (no Clerk call inside that file, kept directly testable) — which refuses outright to touch an **already-approved** row at all (returns `"Tu perfil ya está verificado."`, a dedicated informational screen in `request-form.tsx`, not just an inline error line): no flipping back to `pending`, and critically, no changing `businessName` through this path once approved. Resubmitting while still `pending`/`rejected` matches by `clerkUserId` first, falling back to `userEmail` only for a legacy row that predates this link — matching by `clerkUserId` first is what lets a resubmission survive the applicant's Clerk primary email having changed since an earlier submission, without colliding with that row's own `clerkUserId` unique constraint.

**Verified ↔ sender identity unification (Etapa 7)**: "is this sender verified?" is resolved everywhere by **`clerkUserId`**, never by email — `lib/senders/resolve-verified-status.ts`'s `resolveVerifiedStatusByClerkUserId()` is the single shared lookup used by `checkSendPermission()` (the 3/20 hourly cap), `checkVerifiedStatus()` (the "Perfil verificado" indicator shown to the sender on `/send`), and the buzón's own display below — so the three can never disagree about who's verified. This replaced an earlier email-based match that could miss a sender whose `senders.email` had drifted from their `verified_requests.userEmail` (e.g. after a Clerk primary email change) — confirmed as a real gap, not a hypothetical one, via a direct test with mismatched emails under the same `clerkUserId`. In the buzón, `app/inbox/actions.ts`'s message query left-joins `senders`/`verifiedRequests` live (by `clerkUserId`, `status = 'approved'`) on every render — a verified sender's message shows their real `businessName` **and a "Verificado" badge** (`isVerifiedSender: true` in `MessageDTO`, rendered as a `BadgeCheck` icon in `inbox-content.tsx`, same icon already used for "CAVATAR · Oficial" broadcasts) instead of `"Remitente N"`, and their own free-text "Nombre o alias" is dropped entirely for them — a verified identity is server-confirmed truth, not a self-reported claim worth appending the way Etapa 5's `"Remitente N, dice llamarse..."` pattern does for everyone else. If `businessName` is blank (an approved profile from before this field existed), the fallback is **`"Perfil verificado"` plus the badge — never the sender's email**, since the buzón owner must never see a sender's email under any circumstance, verified or not. Because the join is live, not a point-in-time snapshot, **revoking a profile removes the badge immediately**, even from messages sent while it was still approved — a deliberate choice: a message from someone whose verification was pulled for abuse shouldn't keep flaunting a trust signal that's no longer true. Impersonation is structurally impossible through the free-text alias field: the badge is decided entirely by the server-side `clerkUserId` join, never by anything the sender types or the client supplies — a non-verified sender typing "Verificado" or a fake business name as their alias still only ever renders as `"Remitente N, dice llamarse \"Verificado\""`, never the badge. Once approved, **only the admin can change `businessName`** (`setBusinessName()`, editable from `/admin/verified`'s own "Nombre comercial" column, shown prominently and separately from "Nombre completo" so the admin sees exactly what will go public before approving) — `submitVerifiedRequest()`'s guard above is the other half of that rule, blocking the applicant's own path to changing it post-approval.

**Banners** (`components/banner-slot.tsx` + `lib/banners/get-banner.ts` + `app/admin/banners/*`): one ad image slot per location (`landing` | `send` | `inbox` — `banners.location` is `unique()`, so there's no rotation/carousel; uploading a new image just replaces the old one). `BannerSlot` renders the image (clickable, `rel="sponsored"`, if `link_url` is set) or a dashed-border "Espacio publicitario" placeholder when there's no active banner for that location. Images live in Vercel Blob (`access: 'public'`); `app/admin/banners/actions.ts`'s `uploadBanner()` validates content type (JPEG/PNG/WebP) and size (2MB) before calling `put()`, and calls `del()` on the previous blob whenever a banner is replaced or removed so storage doesn't accumulate orphaned files. `next.config.mjs` bumps `experimental.serverActions.bodySizeLimit` to `3mb` — Next's 1MB default rejected uploads before the app-level 2MB check ever ran, and the real multipart body (boundaries + the `linkUrl` field) needs headroom above the raw file size. **`/`, `/send`, and `/inbox` are all marked `export const dynamic = "force-dynamic"`**: a plain `db.select()` doesn't hint dynamism to Next's static analysis the way `fetch()` does, so without this all three would have prerendered once at build time and frozen whatever banner existed then — defeating the entire point of managing banners without a redeploy. (`/claim` doesn't have this — its own env-var-driven content was already accepted as build-time-frozen, a separate, lower-stakes tradeoff made earlier.)

**Broadcasts** (`app/admin/(protected)/broadcast/*`): lets the admin send an official CAVATAR message via three mutually-exclusive recipient modes, chosen with a `RadioGroup` in `broadcast-manager.tsx` and tracked in `broadcasts.source` (`"all" | "brand" | "list"`, `pgEnum`): every approved plate; just the plates whose `claim_requests.vehicle_brand` normalizes (`lower(trim(...))`, same fragment as the reports brand breakdown) to a brand picked from a dropdown (`fetchBrandOptions()` populates it from actual approved-claim brands with counts, deliberately not a freeform field, so a typo can't silently zero out the recipient list); or an arbitrary list of plates uploaded as an `.xlsx`/`.xls`/`.csv` file, parsed server-side with the `xlsx` (SheetJS) package via `previewBroadcastFile()`. The file-list mode is deliberately **not** filtered against `claim_requests` at all — every valid plate string in the file gets the message regardless of claim/approval status, matching how `/send` already treats a single plate typed by anyone. `extractPlatesFromRows()` looks for a header cell containing "placa" (case-insensitive, any column) and reads that column from row 2 on; with no such header it falls back to column A starting at row 1. Per-cell validation is purely structural (trim, uppercase, non-empty, ≤20 chars — the same bound `/send`'s schema already uses) with no plate-format regex, since CR plate formats vary too much across vehicle types/eras for a stricter check to be safe; invalid or duplicate rows are silently dropped, and the whole upload is capped at 5,000 plates and 2MB. Sending is a two-step flow in all three modes: "Vista previa" fetches the exact recipient count first (a live `claim_requests` count for "all"/"brand", or the parsed-and-deduped plate count for "list"), then the admin has to type that exact number into a confirm field before "Enviar" is enabled. `sendBroadcast()` re-derives the count server-side right before writing (re-querying `claim_requests` for "all"/"brand", re-normalizing the plate array for "list") and refuses to proceed if it no longer matches. The actual fan-out is a single atomic statement either way — `INSERT INTO messages (...) SELECT ... FROM claim_requests WHERE status='approved' [AND lower(trim(vehicle_brand)) = ...]` for "all"/"brand", or `INSERT INTO messages (...) SELECT ... FROM unnest($plates::text[]) AS p(plate_number)` for "list" — chosen specifically because `neon-http` has no interactive-transaction support to fall back on, so atomicity has to come from the statement shape itself: either every matching plate gets the message or none do. Each send is grouped under a `broadcasts` row (`broadcast_id` FK from every `messages` row inserted in that send), which doubles as both an audit trail (who sent what, using which mode/filter, to how many plates, when) and the undo mechanism: "Deshacer" in the broadcast history hard-deletes every `messages` row sharing that `broadcast_id` and stamps `broadcasts.undone_at`. This is explicitly a **partial** undo — it stops the message from showing to anyone who hasn't opened their inbox yet, but can't retract it from someone who already read it, and the UI copy says so rather than overpromising. Official messages never touch `submitMessage()` in `app/send/actions.ts` (the public send path), so `broadcast_id` can only ever be set by an admin-gated Server Action — there's no way for a regular `/send` submission to forge the "CAVATAR · Oficial" badge. `broadcasts.recipient_plates` (nullable `text[]`) is a permanent snapshot of exactly which plates got a given send, captured from the `RETURNING plate_number` of the same fan-out `INSERT` — deliberately a separate column from `messages`, not derived from it at read time, specifically so it survives `undoBroadcast()`'s hard delete: "Deshacer" removes the message from inboxes but the historical record of who received it is kept indefinitely, on purpose (closes the same kind of audit gap flagged elsewhere in Roadmap, rather than opening a new one). `fetchBroadcastRecipients()` (admin-gated, `app/admin/(protected)/broadcast/actions.ts`) reads straight from this column — `null` only for broadcasts sent before the column existed and already undone by the time it was added, where the underlying `messages` rows are genuinely gone and unrecoverable. The "Ver destinatarios" dialog in `broadcast-manager.tsx` lazy-fetches this per entry (not preloaded with the history list, since a single page load could otherwise ship tens of thousands of plate strings for entries nobody opens) and offers "Exportar CSV" using the same `lib/csv/to-csv.ts` + `download-csv.ts` helpers the reports module already uses, entirely client-side against the already-fetched list.

**Admin email notifications** (`lib/email/send-admin-*.ts` + `app/api/cron/daily-digest/route.ts`): two kinds. Immediate: `submitClaim()` (`app/claim/actions.ts`) and `submitVerifiedRequest()` (`app/verified/request/actions.ts`) each `await` a `sendAdminNew*Email()` call right after their insert succeeds — awaited so the send actually completes before the serverless invocation can be torn down, but a failure only gets `console.error`'d, never surfaced to the public submitter, since this is an internal admin ping about somebody else's request, not something the submitter should see or worry about. (Contrast with the existing admin-facing emails in `lib/email/send-claim-rejected-email.ts` etc., whose failures *do* surface as a `warning` in the response — appropriate there because the caller is the admin who just clicked the button, not a public submitter.) Both read the recipient from `ADMIN_NOTIFICATION_EMAIL`, deliberately a separate env var from `ADMIN_EMAILS` — the latter gates who can log into `/admin`, the former is just an inbox for alerts, and there's no reason the two lists need to match. `submitClaim()` also fires `sendClaimReceivedEmail()` (`lib/email/send-claim-received-email.ts`) to the *submitter's own* address — a brief "we got it, we're reviewing it" receipt with no ETA (none has been formally defined), same silent-failure handling as the admin ping, since the on-screen "Tu solicitud fue enviada correctamente" is the real confirmation and the claim row is already committed either way. Both this and the admin ping re-fire on a resubmission (a rejected claim resubmitted through the same form), since that's a genuinely new pending review cycle. Daily digest: Vercel Cron can only call an HTTP endpoint, not a Server Action, so `app/api/cron/daily-digest/route.ts` is a deliberate, one-off exception to this codebase's "no `app/api`, everything is a Server Action" convention — scheduled via `vercel.json`'s `crons` array (`"0 0 * * *"`, i.e. 00:00 UTC = 6:00 PM Costa Rica time, since CR has no DST and is fixed at UTC-6). The route checks `Authorization: Bearer $CRON_SECRET` against the `CRON_SECRET` env var before doing anything — without that, the endpoint would be a public URL anyone could hit to trigger (or spam) the admin digest; `CRON_SECRET` has to be set to the same value in both `.env.local` and the Vercel project's env vars, since Vercel doesn't auto-generate or auto-sync it. The digest queries `claim_requests`/`verified_requests` for `status = 'pending'` and skips sending entirely if both are empty, rather than sending a daily "all clear" — a deliberate choice to keep the digest from becoming ignorable noise on quiet days. On Vercel's Hobby plan, cron execution time isn't guaranteed to the minute (can drift up to about an hour), which only matters here because "6:00 PM" is a target, not a promise.

**Admin panel** (`app/admin/*`): the only UI for reviewing `claim_requests`/`verified_requests`/`banners` and moderating `messages`, plus sending broadcasts (see Broadcasts above). Access is restricted to whatever emails are in the server-only `ADMIN_EMAILS` env var (comma-separated, checked case-insensitively by `lib/auth/is-admin.ts`'s `isAdminEmail()`) — a role in the database was deliberately avoided so access can't be granted by a mutable row, only by deployment config. Two independent layers enforce this, and only one of them is real security: `app/admin/(protected)/layout.tsx` (a Server Component gating every route inside the group) redirects unauthenticated visitors to `/admin/login` and non-admin sessions to `/`, but that's UX only — it never runs for a Server Action invoked directly. The actual boundary is `lib/auth/require-admin.ts`'s `requireAdminEmail()`, called as the first line of every admin Server Action (`app/admin/(protected)/{claims,verified,messages,banners,reports,broadcast}/actions.ts`), returning `{ok:false}` instead of throwing so it fits this codebase's `{success, error?}` action convention. All pre-existing `/admin/*` routes live under an `app/admin/(protected)/` route group (parenthesized folder — no URL segment, just scoped layout inheritance) so that `app/admin/login`, a sibling of the group rather than a child, doesn't inherit that layout's auth guard; without the split, an unauthenticated visit to `/admin/login` would itself get redirected to `/admin/login` and loop forever. `/admin/login` (`page.tsx` + `admin-login-form.tsx`) is a deliberate duplicate of `/verified/login`'s Clerk Signals form (`needs_client_trust`/Client Trust handling, `finalizeAndRedirect`) rather than a shared component — same mechanism, but without the "Crear cuenta" link or "perfil verificado" copy, redirecting to `/admin` (or `?returnTo=`) instead of `/verified/dashboard` on success. Duplication was chosen over extraction specifically to avoid any risk to `/verified/login`, which is already tested and in production. **Unlike every other login page in this codebase, `/admin/login` temporarily offers both methods**: email-code as the primary view, with an "Entrar con contraseña" link to a secondary `signIn.password()` view — see Auth above for exactly why and for how long. A follow-up commit, gated on confirming the email-code path works in Production (see Auth's deployment-order note), removes the password view entirely; until then this file carries real, if temporary, duplication of both auth mechanisms. If a session is already active when `/admin/login` is visited, the page redirects immediately without rendering the form: an admin session goes to `/admin` (or `returnTo`), a non-admin session goes to `/`, mirroring how the `(protected)` layout treats a non-admin session on any other `/admin/*` route.

**Message moderation — soft delete, reports and inbox sessions** (`app/inbox/moderation-actions.ts`, `app/admin/(protected)/messages/actions.ts`, `lib/inbox/session.ts`, `app/api/cron/purge-deleted-messages/route.ts`): closes the Roadmap's original "no audit trail for message deletion" gap and adds an owner-side moderation surface that didn't exist before. `messages` gained `archivedAt` (owner-only declutter — never hides anything from the admin, never a moderation action) and `deletedAt`/`deletedBy` (one soft-delete mechanism shared by the owner's own "Eliminar" — `deletedBy: "owner"` — and the admin panel's default "Borrar" — `deletedBy` set to the admin's own email, a real database audit trail where before there was only a `console.error` line). A new `message_reports` table (`plateNumber`, `messageId` nullable with `ON DELETE SET NULL`, `messagePreview` — a permanent, untruncated snapshot of the full message text captured at report time so the report stays reviewable even after the underlying message is purged, `reason` nullable, `status` `pending | reviewed | dismissed`, `createdAt`, `reviewedAt`, `reviewedBy`) backs the owner's "Reportar" action and the admin's reported-messages queue. A message with `broadcastId` set (an official CAVATAR message) can still be archived or deleted by the owner but can never be reported — `inbox-content.tsx` hides the "Reportar" button entirely for those rows, so there's no path that creates a `message_reports` row behind a broadcast message.

Owner actions on the buzón (`archiveMessage`, `deleteMessage`, `reportMessage` in `app/inbox/moderation-actions.ts`) require a short-lived session instead of re-entering the plate password on every click — the buzón never had any session before this. `lib/inbox/session.ts` issues one on a successful password check (`issueInboxSession()`, called from `verifyPlatePassword()`): a 32-byte opaque random token, only its SHA-256 hash stored in a new `inbox_sessions` table (`plateNumber`, `tokenHash`, `expiresAt`, `createdAt`) — the same "opaque token, hash in the database" pattern as the setup/reset tokens, deliberately not a signed/stateless JWT, so there's one trust mechanism to reason about, not two. The `cavatar_inbox_session` cookie (httpOnly/Secure/SameSite=Lax) holds only the random token, never the plate number, so only the server can map a session back to a plate. The TTL is a 30-minute sliding window: `verifyAndRenewInboxSession(plateNumber)` checks the session's plate matches the message being acted on and, on success, renews the expiry another 30 minutes measured from that action's own time (not from original issuance). Every failure mode — no cookie, an expired session, a session for the wrong plate, or the message not existing at all — returns the identical generic `SESSION_EXPIRED_ERROR` ("Tu sesión venció, volvé a ingresar tu clave."), never distinguished, so none of those cases can be told apart from the outside. `invalidateInboxSessions(plateNumber)` is wired into both `resetPasswordWithToken()` and `revokeClaim()`, same reasoning as their existing `push_subscriptions` cleanup — a password reset or a revoked claim closes any buzón session left open under the old password.

On the admin side, `deleteMessage()` in `app/admin/(protected)/messages/actions.ts` is the same soft delete as the owner's, just with `deletedBy` set to the admin's own email, and it also marks any pending report on that message `reviewed` (deleting the message is itself the resolution a report was asking for). A separate `permanentlyDeleteMessage()` is an immediate, irreversible hard delete for severe cases — bypasses the ~30-day soft-delete window entirely, logs a `console.error` trail (id, plate, admin email, message preview) before deleting, and updates `message_reports` (marking any pending report `reviewed`) **before** the `messages` DELETE runs, not after: once the message row is gone, the FK's `ON DELETE SET NULL` has already cleared `messageId` on any report for it, so a later `WHERE messageId = id` would match nothing and leave the report stuck `pending` forever. `fetchReportedMessages()`/`fetchPendingReportsCount()` back the admin's "Reportados (N)" tab in `messages-table.tsx`; `dismissReport()` marks a report `dismissed` without touching the message, for when the admin reviews it and decides it doesn't warrant deleting anything. `fetchMessages()`/`fetchAllMessagesForExport()` both gained an `includeDeleted` flag (default `false`, filters `deletedAt IS NULL` unless the admin checks "Incluir eliminados") so neither the default table view nor the CSV export surfaces soft-deleted rows unless asked. The admin dashboard (`app/admin/(protected)/page.tsx`) gained a "Reportes pendientes" stat card, and the daily digest (`app/api/cron/daily-digest/route.ts`) now skips sending only when claims, verified requests, **and** pending reports are all zero.

**The daily purge cron** (`app/api/cron/purge-deleted-messages/route.ts`, scheduled in `vercel.json` at `0 9 * * *` UTC — 3:00 AM Costa Rica time, deliberately low-activity and well clear of the digest's `0 0 * * *`/6:00 PM slot): authenticated the same way as `daily-digest`, checking `Authorization: Bearer $CRON_SECRET` and returning 401 without touching anything on a mismatch. Each run does three independent sweeps: (1) hard-deletes every `messages` row where `deletedAt IS NOT NULL AND deletedAt < now() - 30 days` — exactly that condition, never touching `archivedAt` or a row whose `deletedAt` is still null — after first marking any still-`pending` `message_reports` row for those message ids `reviewed` (`reviewedBy: "cron:purge-deleted-messages"`), in that order, for the same `ON DELETE SET NULL` reason as `permanentlyDeleteMessage()` above; (2) deletes every `inbox_sessions` row whose `expiresAt` is already in the past; (3) deletes every `message_reports` row that's already closed — `status` `"reviewed"` or `"dismissed"`, covering both an admin's own resolution and the auto-`"reviewed"` stamp sweep (1) applies when a pending report's message gets purged — and whose `reviewedAt` is more than ~12 months old; a `pending` report is never touched by this sweep no matter how old, since its `messagePreview` may be the only record left once the message it was about is long gone. All three counts are logged via `console.error` and returned in the JSON response (`purgedMessages`, `purgedInboxSessions`, `purgedMessageReports`). Because Vercel Cron on the Hobby plan doesn't fire at an exact minute, both the Términos and the Aviso de Privacidad describe the message retention as "aproximadamente 30 días" rather than exact.

**Reports** (`app/admin/reports/*`): a 5-section analytics dashboard — growth (claim/verified approvals by week or month), activity (messages by day/week, active-vs-dormant approved plates at a 90-day no-message threshold), revenue (approved-plate count × ₡5,000, explicitly labeled an *estimate* in the UI since there's no renewal/expiration tracking at all — payment happens entirely outside the system), vehicle-brand demographics (`claim_requests.vehicle_brand` is freeform text, so the breakdown groups by `lower(trim(...))` to collapse casing/whitespace duplicates, not genuine typos), and claim review turnaround time. Each section is stat cards + a Recharts chart (`components/ui/chart.tsx`, previously vendored but unused until this) + a "Descargar CSV" button (`lib/csv/to-csv.ts` + `download-csv.ts` — hand-rolled CSV, no library, with a UTF-8 BOM so Excel doesn't mangle accented characters). The week/month and day/week time-series queries fill gaps with SQL `generate_series` so a period with zero activity renders as zero instead of a break in the trend line; the interval literals in that raw SQL are spliced in as text from fixed internal constants only, never parameterized — binding an integer parameter against `||` for string concatenation has no matching Postgres operator and throws. Approve/reject only apply to `pending` rows; revoke only applies to `approved` rows and, for a claim, also clears `password_hash`/`failed_attempts`/`locked_until` (cutting inbox access immediately) — for a verified profile, flipping `status` back to `rejected` is sufficient since `checkVerifiedStatus()` in `app/send/actions.ts` checks nothing else. There's no `revalidatePath` anywhere in this codebase (no precedent), so the admin tables use local optimistic state updates instead of re-fetching after a mutation. Message deletion is soft delete by default, with a separate "Eliminar definitivamente" action for an immediate, irreversible hard delete — see Message moderation above for the full soft-delete/report/purge design. `/admin/messages`'s own "Descargar CSV" button (`fetchAllMessagesForExport()`) exports every row matching the currently applied plate filter — not just the visible paginated page, and not the full unfiltered history when a filter is active — via a `plateFilterClause()` helper shared with `fetchMessages()` so the two can't drift apart. The applied filter is tracked as its own state in `messages-table.tsx`, separate from the live search-box text, so exporting after typing a new term but before pressing "Buscar" still exports what's actually on screen.

**Styling**: `app/globals.css` is the active stylesheet (imported from `app/layout.tsx`, referenced by `components.json`'s `tailwind.css`). It defines a light, license-plate-inspired design system as CSS custom properties consumed by Tailwind v4's `@theme` — white background, carbón (`--foreground: #0B1220`) as the dominant color, and two disciplined accents: blue (`--primary: #1839A6`, reserved for the plate-frame element and focus states, not general emphasis) and red (`--destructive: #CE1126`, the hero's brand line plus real error/alert states). `:root` and `.dark` hold identical values — there's no dark-mode toggle anywhere in the app, `.dark` is just inert unused infrastructure. **`styles/globals.css` is dead code** — a leftover default shadcn/ui light theme that nothing imports; don't edit it expecting it to take effect, and prefer deleting it if doing cleanup.

**`.plate-frame` and `.brand-line`** (`app/globals.css`, plain CSS rules) are deliberately declared *outside* any `@layer` block. Tailwind v4's own utilities live in `@layer utilities`, which outranks `@layer components` regardless of where either is physically written in the file — a `.plate-frame` inside `@layer components` silently loses its 5px border to `Input`/`Card`'s own 1px `border` utility. Unlayered CSS beats every `@layer`-wrapped rule, so that's how these two are kept reliable. `.plate-frame` (thick blue border + two corner "screw" dots) is intentionally rare: the plate-search inputs on the landing hero and `/inbox`, and at most one "featured" card per message list (currently just "the most recent message," since `messages` has no read/unread tracking to genuinely target the newest-unread one).

Fonts, loaded via `next/font/google` in `app/layout.tsx`: Inter (`--font-inter`, body/forms/messages, the default `font-sans`), Archivo Black (`--font-plate`, **only** the "CAVATAR" wordmark and plate numbers shown as data/typed into a plate search field — never section titles), and Archivo 600/700 (`--font-label`, labels/nav/status text/timestamps, uppercase with wide tracking). Page-level H1s (e.g. "Iniciar sesión", "Reclamar placa") deliberately use neither special font — they're plain Inter bold, normal case.

Disabled buttons (`components/ui/button.tsx`) use a neutral `disabled:bg-muted disabled:text-muted-foreground disabled:border` treatment, not reduced opacity — on this palette, translucent carbón/blue reads as a washed-out pale blue rather than "unavailable," and solid-variant buttons have no border at all by default so a color-only disabled state was invisible on some screens (e.g. behind an unchecked consent checkbox).

`components/ui/` is the shadcn/ui component library (57 generated primitives) — treat as vendored code; prefer composing over hand-editing unless fixing a real bug. `components/*.tsx` (hero, explanation, features, faq, footer) are the marketing landing-page sections composed in `app/page.tsx`.

Path alias: `@/*` maps to the repo root (see `tsconfig.json` and `components.json` aliases: `@/components`, `@/lib`, `@/ui`, `@/hooks`).

**PWA (Phase 1 — installable only, no offline support)**: `app/manifest.ts` exports `MetadataRoute.Manifest` (served at `/manifest.webmanifest`, auto-linked by Next — no manual `metadata.manifest` entry needed). `app/layout.tsx` carries a separate `export const viewport: Viewport = { themeColor: '#0B1220' }` — `metadata.themeColor` is deprecated in Next's own types in favor of this — plus `metadata.appleWebApp` (`statusBarStyle: 'default'`, not `'black-translucent'`, since the app has a white background and no safe-area-inset handling, so an overlaid status bar would risk unreadable content). The icon set (`public/icon-192.png`, `icon-512.png`, `icon-512-maskable.png`, `apple-icon.png`, `favicon.png` — the white-"C"-on-carbón-with-a-red-dot monogram) is generated by `scripts/generate-pwa-icons.mjs`, re-run manually whenever the monogram design changes (not part of the build). That script deliberately never renders text at rasterize time: `opentype.js` (a devDependency, pure JS) extracts the real "C" glyph's vector outline from `@fontsource/archivo-black` (also a devDependency — font files only, nothing from this package ships in the runtime bundle) once, embeds it as a plain SVG `<path>` alongside a background `<rect>` and accent `<circle>`, and `sharp` (devDependency) rasterizes that pure-vector SVG to each target PNG size — by the time `sharp` touches it there's no font involved at all, just shapes, specifically to avoid cross-platform font-loading inconsistency in canvas/satori-style text-rendering approaches. The maskable icon shrinks the whole composition (glyph + dot) by the standard 80% safe-zone factor so OS launcher mask shapes can't clip it, while the background still fills edge-to-edge as the maskable spec requires. `components/install-prompt.tsx` (mounted globally in `app/layout.tsx`, next to `{children}`) shows an "Instalar CAVATAR" bar: on Android/Chrome via the `beforeinstallprompt` event (hand-declared as a local `BeforeInstallPromptEvent` interface — not a standard DOM type), on iOS as static Share-sheet instructions (iOS has no `beforeinstallprompt` at all). Hidden when already installed (`display-mode: standalone` or `navigator.standalone`), hidden on every `/admin/*` route (`usePathname()` check — operator-only area, not the install audience), dismissible with a 14-day `localStorage["cavatar_install_prompt_dismissed_at"]` cooldown, and hides itself immediately on the `appinstalled` event if the user installs mid-session through the browser's own UI rather than the bar's button. **No service worker exists or is needed for this phase** — confirmed directly against Chrome's official documentation (`developer.chrome.com/blog/update-install-criteria`) that the service-worker requirement for `beforeinstallprompt`/install-from-menu was removed in Chrome 108 (mobile) / 112 (desktop); Safari's "Agregar a pantalla de inicio" never required one. `proxy.ts`'s existing `clerkMiddleware` matcher already excludes the manifest and every icon file (any path containing a `.` is excluded by the matcher's negative lookahead) — confirmed with `curl` against a production build, not just by reading the regex. Phase 2 (push notifications, offline caching) is explicitly not started; if it ever is, do not cache `/inbox` or `/admin/*` responses — both are session/auth-sensitive.

## Roadmap / known gaps

- **No audit trail for *permanent* message deletion.** Soft delete (the owner's own "Eliminar", and the admin panel's default "Borrar") now records `deletedBy` directly in the database — a real improvement over the original gap. What's left: the admin panel's separate "Eliminar definitivamente" action (`permanentlyDeleteMessage`) still only logs a `console.error` trail (in Vercel's logs, not the database) before hard-deleting, and the daily purge cron (see Message moderation above) eventually hard-deletes every soft-deleted message ~30 days later regardless, at which point the newer `deletedBy` record is gone too. Considered proportionate for a single-admin MVP; revisit if message volume or dispute risk grows.
- **`reviewed_at` has no matching `reviewed_by`.** `claim_requests`/`verified_requests` track when an admin last reviewed a row but not which admin, since `ADMIN_EMAILS` holds a single address today and the column would carry no information until there's a second admin. Add `reviewed_by` if that changes.
- **Claim-email verification is still out-of-band.** The claim-setup-link fix (see Inbox flow above) closes the "race to set a password" vulnerability, but `submitClaim`'s email field is never independently verified (no Clerk-style confirmation) — the admin approving a claim is the only checkpoint that the submitted email belongs to the real plate owner. Someone submitting a claim with their own email before the real owner does is a different, unaddressed problem.
- **Buzón password minimum is still 6 characters.** Both `setupPasswordWithToken()` and `resetPasswordWithToken()` enforce the same 6-character floor as the original setup flow. Worth raising to 8 in both places together, so they don't drift apart again.
- **No account-wide (or per-IP/network) cap on password-reset requests.** `password_reset_window_count`'s 5/24h cap is per-plate only — someone sweeping many different plate numbers could still generate a burst of emails across the whole account, since there's no IP capture in this codebase to rate-limit against (see the earlier abuse-surface audit). Deliberately out of scope for this pass.
- **`revokeVerifiedProfile()`'s outgoing email is only tested with code, never confirmed as a real delivered email.** Same limitation as everywhere else in this codebase a real Clerk-gated flow can't be driven end-to-end in this environment — the revoke action itself and its DB effects (status, badge disappearing live) are real-tested, but whether `sendVerifiedRevokedEmail()` actually lands in an inbox has only been exercised by code review, not a live send confirmed by the user.
- **The `+clerk_test` test accounts created while testing Etapa 7 (e.g. `cavatarverif7+clerk_test@example.com`) are left in Clerk Development on purpose.** Clerk's own convention for these addresses means they're inert test fixtures, not real people — there's no cleanup obligation on the Clerk side the way there is for this codebase's own Neon tables (which this session always does clean up). Don't go looking for a Clerk-side deletion step; it was a deliberate omission, not an oversight.
- **Verify in production, with real QStash, that silenced-sender messages get stamped `owner_notified_at` across all three early-return branches of the webhook** (daily cap, cooldown, nothing pending) — `computeUnnotifiedSplit()`'s own query and the stamping call around it are tested against real code (see Send flow above), but the full `POST` handler's branching sequence can't be exercised end-to-end against `localhost` (same QStash limitation noted there), so this specific ordering is confirmed by code reading, not an automated test.
- **A plate where every pending message happens to be from a muted sender still burns a QStash `publishJSON` call it never needed.** `scheduleOwnerNotificationIfNeeded()` in `app/send/actions.ts` schedules unconditionally, same as before Etapa 5's muting — it has no cheap way to know ahead of time that the webhook will find nothing eligible once it actually runs and applies the muted-sender filter. Accepted: the webhook still correctly sends nothing and stamps `owner_notified_at` either way (see Send flow above), this only wastes a sliver of the account-wide QStash daily quota in the specific case where a plate's *only* recent correspondent is someone the owner has silenced — a narrow, low-frequency scenario, not worth complicating the scheduling path's own logic to special-case.
- **`checkSendPermission()`'s per-sender hourly cap can be exceeded by a message or two under simultaneous sends.** It counts `messages` for that sender, then the caller inserts, as two separate statements — `neon-http` has no interactive transactions to make that atomic. Two requests from the same sender arriving at nearly the same instant could both read a count just under the cap and both proceed, overshooting the real 3/hour (or 20/hour, verified) limit by 1-2 messages. Accepted as a minor, low-stakes race for a per-sender anti-spam cap, not worth the complexity of a stricter mechanism.
- **CSV export uses `,` as the delimiter — Excel under a Spanish regional locale opens it as one single column instead of splitting it.** Affects every CSV this codebase generates via `lib/csv/to-csv.ts` (messages, reports, broadcast recipients), not just the messages one. Worth switching to `;` (the delimiter Excel expects under `es-*` locales) or adding a `sep=,` hint line / BOM-based override — minor, cosmetic, not a data-correctness issue (the CSV itself is valid either way).
- **Open legal question for Ley 8968 counsel: does data cancellation also require erasing the message body itself (`messages.message`/`message_reports.messagePreview`)?** `anonymizeSender()` rewrites `senders.email`, clears `message_reports.reported_sender_email_snapshot`, and clears `messages.contact`/`messages.alias` for that sender's own messages — but it never touches `messages.message` or a report's `messagePreview`, since the message body is the content of an exchange between two people, not solely the sender's own account data, and erasing it could also remove something the *recipient* (the plate owner) has a legitimate reason to keep. Whether erasure needs to reach that far is a legal determination, not a code one.
- **Unify voseo/tuteo across error messages.** Some use voseo ("Probá de nuevo", "Volvé a ingresar tu clave") and some use tuteo ("Intenta nuevamente") — grew inconsistent across etapas built at different times. `/privacidad`, `/terminos`, the FAQ, and `/send`'s privacy checkbox were all converted to tuteo in Etapa 8; this item is now scoped to error-message copy elsewhere in the app, not the legal pages. Low priority, purely a copy consistency issue, not a correctness one.
- **Remove the "documento de trabajo" draft notice from `/privacidad` and `/terminos` once legal counsel signs off.** Both pages currently open with a visible banner saying this is a working draft pending professional legal review — appropriate while the open legal questions in this Roadmap remain unresolved, but it should come down once a lawyer actually reviews the Etapa 8 text.
- **No automatic purge for inactive sender data.** `/privacidad` (section 8) now states senders' data is kept until cancellation or a maximum of 10 years of inactivity, matching the same cap already declared for every other data category — but today that 10-year cap depends entirely on a manual process, there's no cron that enforces it the way `purge-deleted-messages` does for messages. Needs an automated purge for senders inactive past that window.
- **For legal counsel: confirm the actual source of the "10 years" retention cap.** `/privacidad` (section 8) states a flat 10-year maximum retention but no longer cites a specific Ley 8968 article for it (the citation was removed from the public text pending this confirmation) — needs a lawyer to confirm the real basis (a specific article, the Reglamento, or general best practice) before the public text cites one again.
- **`/admin/login`'s password fallback is a deliberate, temporary exception and must be removed.** Etapa 3.5 left `signIn.password()` working there as a secondary "Entrar con contraseña" view specifically to protect Production admin access during the email-code migration — see Auth's deployment-order note above. Once the email-code path is confirmed working in Production and "Sign-up with password" is turned off there, open a follow-up commit that deletes the password view from `admin-login-form.tsx` entirely (and its `password`/`view` state), so this codebase goes back to having exactly one auth mechanism per login page.
- **Reports' day/week/month buckets aren't pinned to Costa Rica's calendar.** `app/admin/(protected)/reports/actions.ts`'s raw SQL (`generate_series`/`date_trunc`) buckets by Postgres's session timezone, not explicitly `America/Costa_Rica` — unlike every other displayed date in the app (see Message moderation's sibling fix, `lib/dates/format-date.ts`), which was fixed everywhere except here. A message sent late at night Costa Rica time could still get counted into the wrong day/week bucket in the growth/activity charts, even though the displayed period *label* itself is now correct. Out of scope for that fix since it means touching the hand-tuned raw SQL CLAUDE.md already flags as sensitive, not just a JS formatting call — revisit as its own task.
